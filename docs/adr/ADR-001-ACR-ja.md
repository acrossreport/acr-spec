## 1. 背景と課題

帳票出力システムの現場では、以下の慢性的な問題が存在する。

- **環境依存の出力差異:** 実行環境（OS、プリンタードライバー、フォントレンダラー）によってピクセル単位のズレが発生し、帳票の品質保証が困難である。
- **既存エンジンの限界:** 市販の帳票エンジンはブラックボックスであり、現場固有の運用要件（複雑なセクション構造、動的レイアウト）への対応に限界がある。
- **プレビューと印刷の乖離:** WYSIWYG を謳う製品であっても、プレビューと実際の印刷結果が一致しないケースが頻発する。
- **ライセンスと保守性:** 特定ベンダーへの依存はライセンスコストと技術的負債を生む。

これらの課題を解決するため、独自帳票エンジン **ACR (Across Report Renderer)** を設計・開発する。

## ADR-001: レンダリングエンジンに Google Skia を採用する

### コンテキスト

帳票の最終出力（PDF・画面プレビュー）を生成するグラフィックスエンジンの選定が必要である。候補として以下を検討した。

- **GDI/GDI+:** Windows 専用。ピクセル精度に問題がある。
- **Cairo:** クロスプラットフォームだが、テキストレンダリングの品質がフォントエンジン依存で不安定。
- **Skia:** Google Chrome・Android・Flutter の描画基盤。ピクセル精度が高く、PDF 直接出力をサポート。
- **PDFium:** PDF 生成専用。インタラクティブプレビューには不向き。

### 決定

**Google Skia を ACR の唯一のレンダリングエンジンとして採用する。**

### 理由

1. **ピクセル精度の一貫性:** Skia は画面描画と PDF 出力で同一のパスを使用するため、プレビューと印刷結果が理論上一致する。
2. **プラットフォーム中立性:** Windows・macOS・Linux で同一の描画結果を保証できる。
3. **実績:** 世界最大規模のブラウザエンジン (Chrome) が採用しており、品質・安定性の実績が十分にある。
4. **PDF 直接生成:** `SkDocument` による PDF 出力が可能であり、中間変換レイヤーを排除できる。
5. **フォントレンダリング:** FreeType / DirectWrite / CoreText との統合により、OS 標準フォントエンジンを正確に利用できる。

### 結果として生じるトレードオフ

| 利点 | 不利点 |
|------|--------|
| 高精度なピクセル一致 | ネイティブライブラリのビルド・配布が必要 |
| PDF・画面描画の統一パス | Skia API の習熟コスト |
| クロスプラットフォーム保証 | バージョン管理が Chromium リリースサイクルに準ずる |

## ADR-002: テンプレート形式に JSON 中間描画モデルを採用する

### コンテキスト

帳票定義（テンプレート）の形式として、XML・独自バイナリ・JSON 等を検討した。帳票エンジンにおいてテンプレートは「意図の記述」と「描画命令」の橋渡しをする中核的な存在である。

### 決定

**JSON を ACR テンプレートの唯一の中間描画モデル形式とする。**

JSON は単なるデータ形式ではなく、ACR における **「描画意図を表現する中間言語」** として位置づける。

### 理由

1. **人間可読性:** XML と比較してノイズが少なく、テンプレート開発・デバッグが容易である。
2. **型安全なスキーマ定義:** JSON Schema による厳密なバリデーションが可能。
3. **ツールチェーンとの親和性:** ビジュアルエディタ・差分管理・CI/CD との統合が容易。
4. **中間モデルとしての明確な責務:** JSON テンプレートは「何を描くか」を定義し、Skia レイヤーが「どう描くか」を担う。関心の分離が明確である。
5. **動的生成の容易さ:** データバインディングや条件分岐ロジックを JSON 構造として表現できる。

### JSON テンプレートの基本構造（概念）

```json
{
  "version": "1.0",
  "pageSize": { "width": 210, "height": 297, "unit": "mm" },
  "sections": [
    {
      "type": "ReportHeader",
      "height": 20,
      "elements": [
        {
          "type": "TextBox",
          "x": 10, "y": 5, "width": 190, "height": 10,
          "text": "{{ reportTitle }}",
          "font": { "family": "IPAex明朝", "size": 14, "bold": true },
          "alignment": "center"
        }
      ]
    }
  ]
}
```

### 結果として生じるトレードオフ

| 利点 | 不利点 |
|------|--------|
| 人間可読・バージョン管理容易 | バイナリより冗長でファイルサイズが大きい |
| スキーマバリデーション可能 | JSON Schema の保守コスト |
| ツールチェーン統合が容易 | 複雑な式・スクリプトの表現に制約がある |

## ADR-003: ActiveReports 互換のセクション構造を採用する

### コンテキスト

ACR の帳票レイアウト体系として、現場で広く普及している ActiveReports のセクション構造（PageHeader / GroupHeader / Detail / GroupFooter / PageFooter / ReportHeader / ReportFooter）を参照設計として採用するかどうかを検討した。

### 決定

**ActiveReports 互換のセクション構造を ACR の標準レイアウトモデルとして採用する。**

ただし、ACR の独自拡張を妨げるものではなく、互換性は「設計上の出発点」である。

### 理由

1. **現場の知識資産の活用:** 多くの現場エンジニアが ActiveReports の概念を理解しており、学習コストを最小化できる。
2. **移行コストの低減:** 既存の ActiveReports 帳票定義を ACR へ段階的に移行しやすい。
3. **実績のある設計:** ActiveReports のセクション構造は30年以上の帳票業務に裏打ちされた設計であり、現場の運用要件を高度に反映している。
4. **グループ集計・改ページ制御の表現力:** セクション構造は複雑な集計帳票・改ページ条件を自然に表現できる。

### セクション定義

| セクション | 役割 |
|------------|------|
| `ReportHeader` | 帳票全体の先頭に1回だけ出力 |
| `PageHeader` | 各ページの先頭に出力 |
| `GroupHeader` | グループの先頭に出力（ネスト可） |
| `Detail` | 明細レコードごとに繰り返し出力 |
| `GroupFooter` | グループの末尾に出力（ネスト可） |
| `PageFooter` | 各ページの末尾に出力 |
| `ReportFooter` | 帳票全体の末尾に1回だけ出力 |

### 結果として生じるトレードオフ

| 利点 | 不利点 |
|------|--------|
| 現場エンジニアの習熟が不要 | 完全 ActiveReports 互換の維持コスト |
| 既存帳票資産の移行容易性 | 独自設計の一部が制約を受ける可能性 |
| 実績ある設計思想の継承 | ActiveReports の設計上の問題点も引き継ぐリスク |

## ADR-004: WYSIWYG 精度を最優先設計原則とする

### コンテキスト

帳票エンジンの品質を測る最重要指標として、「プレビューと印刷結果の一致精度」を設計原則の最上位に置くかどうかを検討した。

### 決定

**ACR は「1ドットの狂いもないWYSIWYG」を最優先設計原則とする。**

これは性能・開発速度・互換性よりも優先される不変の原則である。

### 理由

1. **帳票の社会的責任:** 請求書・納品書・給与明細等の法的効力を持つ帳票において、プレビューと印刷の差異はビジネスリスクおよび法的リスクになり得る。
2. **現場の信頼:** 「プレビューで確認した通りに印刷される」という信頼が、現場オペレーターの生産性の基盤である。
3. **デバッグコストの削減:** プレビュー・印刷の一致が保証されることで、環境差異に起因するバグの調査コストが大幅に削減される。

### 実装上の制約

- 座標計算・テキスト配置・改ページロジックのすべてにおいて、Skia の同一 API パスを画面描画と PDF 生成で共用する。
- フォントメトリクス（グリフの幅・高さ・カーニング）は実行時にキャッシュし、プレビューと PDF 出力で同一の値を参照する。
- サブピクセル単位の端数は常に同一の丸めルール（切り捨て/切り上げ）を適用する。

## ADR-005: 実機不要プレビュー哲学を採用する

### コンテキスト

帳票エンジンの開発・検証サイクルにおいて、「実際のプリンターや帳票出力装置がなくても完全なプレビューが可能か」を設計指針とするかどうかを検討した。

### 決定

**ACR は「実機不要の哲学」を設計の中心に置く。**

プリンター・帳票端末・専用用紙がなくても、開発者・運用担当者が正確なプレビューを確認できることを保証する。

### 理由

1. **開発効率:** 実機セットアップなしに帳票テンプレートの作成・修正・確認サイクルを高速化できる。
2. **CI/CD への統合:** 自動テストパイプラインでプレビュー画像を生成・比較することで、帳票のリグレッションテストが可能になる。
3. **地理的・コスト的制約の解消:** 開発拠点と印刷設備が異なる場合でも、リモートで正確な出力を確認できる。
4. **特許レベルの差別化:** 「実機なしに1ドットの狂いもないプレビュー」は、ACR の核心的な技術的優位性である。

### 実現のための技術要件

- Skia の `SkSurface` を使用したオフスクリーンレンダリングによる PNG/JPEG プレビュー生成。
- 用紙サイズ・マージン・解像度（DPI）のソフトウェアシミュレーション。
- フォント埋め込みによる環境非依存のテキストレンダリング。
- 仮想プリンタードライバー不要の純粋ソフトウェアスタックの維持。
